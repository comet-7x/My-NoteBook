AI的时代已经来临，它重新定义了新时代下程序员的代码开发规范，我们要真正要解决的，不是“少用 AI”，而是建立一种新的开发方式：
>AI 可以参与写代码，但代码的理解权、设计权、修改权必须留在你手里。

过去一年，我的流程大概是：
需求 → 想个大概 → AI 出方案 → AI 实现 → AI 写测试 → 跑通 → AI 写文档 → 粗看代码 → 结束

这个流程最大的危险不是代码质量，而是它绕过了程序员最重要的几个认知过程：

**问题建模 → 设计取舍 → 数据流理解 → 实现细节 → Debug → 建立心智模型 → 长期记忆。**

所以我最后得到的是：

> “我拥有这个项目的代码，但我并不拥有这个项目的知识。”


## 一、先不要想着“戒 AI”

如果你现在给自己定目标：

> 从今天开始不用 AI，所有代码自己写。

大概率坚持不了，而且意义也不大。

因为现代开发本来就会越来越依赖 AI。

真正应该训练的是：

> **即使 AI 写出了 80% 的代码，我依然能够理解 100% 的关键路径，并且能够独立维护它。**

这是接下来所有行动的总目标。

我建议你把未来 1～2 个月的目标收缩成一句非常明确的话：

> **任何我负责的核心模块，在完成之后，我必须能够脱离 AI，讲清楚它为什么这么设计、数据怎么流动、关键代码在哪里、哪里可能出错，以及需求变化时应该修改哪里。**

以后衡量自己，不再问：

> “这个功能做完了吗？”

而是问：

> “这个功能现在属于我了吗？”

## 二、你现在的问题，其实可以拆成 5 层

|层级|你目前容易发生的情况|以后应该达到的状态|
|---|---|---|
|问题理解|知道“大概要做什么”|能定义输入、输出、约束、边界|
|方案设计|AI 给方案，你选一个|你先形成方案，AI负责挑战和补充|
|代码实现|AI一次写很多|小步实现，每一步理解|
|验证|测试通过 = 完成|测试 + 数据流 + 边界 + Failure case|
|内化|粗略看一遍代码|能脱离代码重新讲出来|

你现在最严重的不是第五层。

而是：

**第二、三、四层大量被 AI 跳过去了，导致第五层根本不可能自然形成。**

所以不能靠：

> “以后我认真看代码。”

解决。

因为“看代码”是被动输入。

真正形成理解，需要：

> **预测 → 阅读 → 修改 → 解释 → 回忆。**

---

## 三、从今天开始，加入一个最重要的东西：理解门槛

以后一个 AI 功能完成之后，不允许马上进入下一个任务。

先过一个：

### Understanding Gate

也就是：

> **理解验收。**

至少回答下面这些问题。

|问题|你需要达到的程度|
|---|---|
|这个模块解决什么问题？|30 秒讲清楚|
|输入是什么？|能说出结构|
|输出是什么？|能说出结构|
|核心调用链是什么？|能画出来|
|最重要的 3 个函数是什么？|知道各自职责|
|状态存在哪里？|能指出|
|哪些东西是外部依赖？|知道|
|为什么这样设计？|至少知道主要 trade-off|
|最容易出错在哪里？|能说出 2～3 个|
|我要新增一个需求改哪里？|能定位|
|如果某段代码删除会怎样？|大致知道影响|

假如其中一半回答不上来：

**这个功能在你的认知层面还没有完成。**

哪怕测试全绿。

---

## 四、你的开发流程要彻底换掉

以后不要再：

> “帮我实现 XXX。”

然后等 AI 输出几百行。

改成下面这个循环。

### 阶段 A：你先思考，但只要求思考 10～20 分钟

不要逼自己一上来设计完整系统。

只写一张很短的 **Development Brief**：

```
## 问题

我要解决什么问题：

## 输入

输入是什么：

## 输出

输出是什么：

## 当前已有东西

哪些模块已经存在：

## 我认为的大致流程

A
→ B
→ C
→ D

## 我不确定的地方

1.
2.
3.

## 我目前倾向的设计

……
```

注意这里有一个非常重要的变化：

以前：

> 不知道 → 问 AI。

以后：

> **先暴露自己到底不知道什么 → 再问 AI。**

这是两个完全不同的学习过程。

---

## 五、第一次问 AI，不准让 AI 写代码

这是我认为对你最重要的一条。

你可以这样问：

```
先不要写代码。

这是我要解决的问题：
……

这是我当前考虑的方案：
……

请帮我：

1. 检查我的问题拆解是否完整
2. 找出我遗漏的边界条件
3. 给出最多 3 种设计方案
4. 比较每种方案的复杂度、扩展性、维护成本
5. 指出我的思考中可能存在的问题

不要直接实现。
```

这样 AI 的身份就从：

**Developer**

变成：

**Senior Engineer / Reviewer**

而你还是 Developer。

这是你重新夺回能力最快的一步。

---

## 六、然后你必须自己做一次方案选择

AI 给你：

方案 A / B / C。

不要直接说：

> “用 A，开始写。”

先自己写：

```
我选择方案 B。

原因：

1. 当前数据量不大，不需要方案 C 的复杂度
2. 方案 A 会让 XX 和 XX 强耦合
3. B 比较适合目前项目规模

缺点：

1. 后续 XX 可能需要重构
2. ……
```

然后发给 AI：

> 帮我检查这个判断有没有问题。

这个动作看起来很小。

但它训练的是程序员最重要的能力之一：

**Trade-off。**

高级工程师真正比初级工程师强的地方，往往不是：

> 会不会 Factory Pattern。

而是：

> 知道什么时候根本不应该用 Factory Pattern。

---

## 七、AI 一次写代码的粒度必须缩小

这是你现在必须强制执行的规则。

过去可能是：

> 实现整个 RAG ingestion pipeline。

以后应该变成：

```
先实现第一个阶段：

RawDocument
→ ParsedDocument

暂时不要实现 chunking、embedding、Milvus。

完成以后解释：

1. 每个类的职责
2. 数据结构
3. 调用关系
4. 为什么这样设计
```

然后你自己跑。

理解。

修改。

再进入：

```
ParsedDocument
→ Chunk
```

最后：

```
Chunk
→ Embedding
→ VectorStore
```

你的开发节奏应该变成：

> **设计一点 → 写一点 → 理解一点 → 测一点 → 修改一点。**

而不是：

> **AI 一口气生成整个系统 → 你开始考古。**

---

## 八、特别重要：禁止 AI 给你“超过你认知层级”的抽象

你提到一句非常关键的话：

> AI 写出来的代码很高级，很抽象，我也看不懂。

这件事情必须马上管住。

因为 LLM 很喜欢生成一些“看起来很工程化”的结构：

```
BaseProcessor
AbstractProcessor
ProcessorFactory
ProcessorRegistry
ProcessorContext
ProcessorStrategy
ProcessorManager
```

你的需求可能其实只有：

```
def parse_document():
    ...

def chunk_document():
    ...

def store_chunks():
    ...
```

所以以后给 AI 一个长期约束：

```
优先使用最简单、最显式、最容易维护的实现。

除非确实必要，否则不要引入：

- 工厂模式
- 复杂继承体系
- 元类
- 过度 Protocol / Generic
- 多层 Wrapper
- Registry
- Dependency Injection
- Event Bus
- 不必要的 async
- 为未来可能存在的需求提前抽象

如果存在更简单的实现，优先简单实现。

任何抽象都必须解释它目前解决了什么实际问题。
```

甚至你可以增加一句：

> **代码应该以“一年后的我仍然能快速读懂”为设计目标，而不是展示高级编程技巧。**

这是非常好的工程原则。

---

## 九、建立一个“抽象预算”

以后看到 AI 新建一个抽象层，问一句：

> **如果把这个抽象删掉，代码真的会明显变差吗？**

例如：

```
class DocumentParserFactory:
    ...
```

问：

为什么需要 Factory？

如果答案只是：

> “为了未来扩展 PDF、DOCX、PPTX……”

但是现在其实只有 PDF。

那就先：

```
def parse_pdf():
    ...
```

以后真的出现：

```
PDF
DOCX
PPTX
HTML
Markdown
```

再抽象。

你可以记一个很实用的原则：

> **重复出现以后再抽象，而不是预测未来以后提前抽象。**

所谓“高级”，很多时候不是更多 abstraction。

而是：

> **知道哪些 abstraction 不需要存在。**

---

## 十、AI 写完代码以后，不要第一时间看解释

这里有一个非常强的学习方法。

AI 写完一个函数，例如：

```
async def retrieve(query):
    ...
```

先不要让 AI：

> “给我详细解释一下。”

你自己先做一件事：

### 预测代码。

先写：

```
我猜它应该：

1. query embedding
2. vector search
3. rerank
4. 返回 documents
```

然后读代码。

你会开始发现：

> 原来这里还有 metadata filter。

> 为什么这里先 deduplicate？

> 为什么这里用了 semaphore？

这种“预测 → 对比”的学习效果，比：

> AI 给我逐行解释。

强很多。

因为后者很容易产生：

**理解错觉。**

你看的时候：

> 嗯嗯嗯，有道理。

关掉以后：

> ……

什么都说不出来。

---

## 十一、每个核心模块必须做一次“闭卷复述”

功能完成以后，把代码关掉。

不要看 AI。

拿纸、白板、Markdown 都可以。

重新写：

```
请求进来
↓
API Router
↓
LessonPlanService
↓
KnowledgeDocument
↓
ChatAgent
↓
Prompt Builder
↓
LLM
↓
LessonPlanResponse
```

然后解释：

> 为什么需要 Service？

> 为什么不是 Router 直接调用 Agent？

> 数据在哪一步转换？

> 哪一步可能失败？

如果画不出来：

重新看。

然后再关掉。

再画。

直到基本一致。

这才叫：

**建立 Mental Model。**

---

## 十二、你尤其应该训练“修改能力”，而不是“阅读能力”

很多人会告诉你：

> AI 写完以后仔细阅读。

我认为还不够。

因为你可能阅读 20 分钟：

> 都看懂了。

然后让我问：

> 把同步调用改成并发调用。

立刻不会。

真正判断代码是不是你的，一个非常简单的标准：

> **你能不能修改它？**

所以每个 AI 模块完成以后，人为做一个小 modification exercise。

例如本来：

```
retrieve top_k=5
```

自己改成：

```
不同 document_type 使用不同 top_k。
```

或者：

```
增加 timeout。
```

或者：

```
增加 metadata filter。
```

或者：

```
把一个异常处理逻辑修改掉。
```

原则：

> **必须有至少一处修改是你自己完成，而不是告诉 AI “帮我改”。**

这个训练会极大提升代码 ownership。

---

## 十三、Debug 权不能完全交给 AI

你现在还需要防止另一种依赖：

```
报错
↓
复制
↓
问 AI
↓
AI 修
```

长时间这样做，会导致 Debug 能力退化得非常厉害。

以后建立一个 **20 分钟规则**。

遇到 bug：

前 20 分钟不允许 AI 直接给答案。

你先完成：

```
Expected:
我认为应该发生什么？

Actual:
实际发生了什么？

Boundary:
最早从哪里开始不符合预期？

Hypothesis:
我目前怀疑哪三个原因？

Evidence:
有什么证据支持/反驳？
```

然后再问 AI：

```
这是我的分析：

……

不要直接给我修复代码。

先判断我的定位思路哪里可能有问题，
再给我下一步应该观察什么变量。
```

AI 就会从：

**修电脑的人**

变成：

**Debug 教练。**

---

## 十四、测试通过绝对不能再等于“我理解了”

你现在的路径：

> AI 写测试 → 测试通过 → 功能 OK。

这个逻辑只能证明：

> 代码满足了测试定义的行为。

不能证明：

> 你理解代码。

以后把完成定义拆成三个：

|验收|问题|
|---|---|
|Functional|能不能跑？|
|Engineering|边界、异常、维护性有没有问题？|
|Cognitive|我理解了吗？|

只有三者都通过：

> Done。

否则最多叫：

> Works.

而不是：

> Done.

---

## 十五、你的文档习惯也需要改

你说：

> 然后开始迷糊地让 AI 写 API 文档、使用文档，看一遍觉得有道理。

这里很容易产生一种现象：

> **文档写得比开发者本人理解得还清楚。**

这是一个危险信号。

以后文档顺序改成：

**你解释 → AI 整理。**

例如你先写很粗糙的：

```
POST /lesson-plan

输入：
KnowledgeDocument

里面主要有课程信息、知识点。

service 会先……
然后调用……

失败可能：
LLM timeout
格式解析失败
……
```

然后告诉 AI：

> 在不增加我没有表达过的设计结论的情况下，帮我整理成规范 API 文档。

这样文档是在：

> **固化你的理解。**

而不是：

> **替代你的理解。**

## 十六、以后真正值得保存的不是“大量文档”

一个模块我建议你只保留三种东西。

|文档|用途|
|---|---|
|Architecture Note|它到底怎么工作|
|ADR|为什么这么设计|
|Usage / API|怎么使用|

其中最重要的是 **ADR**。

例如：

```
# 为什么 LessonPlan 使用 ChatAgent 而不是 Workflow

背景：

当前任务主要是：
KnowledgeDocument → LessonPlan

候选方案：

A. 单 ChatAgent
B. 多 Agent
C. LangGraph Workflow

决定：

当前使用 A。

原因：

目前任务没有复杂状态机；
多 Agent 会提高复杂度；
单 Agent 更容易调试。

什么时候需要重新评估：

出现多轮教师反馈、
多角色协作、
长流程状态保存时。
```

半年以后你回来：

马上知道：

> 当时为什么这么干。

这个东西比 3000 字 AI 自动生成的“系统设计文档”有价值很多。

---

## 十七、给自己建立一个非常具体的“代码所有权评分”

以后每个模块完成，给自己打分。

|分数|状态|
|---|---|
|0|AI 写的，我只知道能跑|
|1|大概知道在干什么|
|2|能说明主要函数|
|3|能画出调用链和数据流|
|4|能解释主要设计决策并独立修改|
|5|能脱离 AI 重写核心逻辑|

你的目标不是所有代码都做到 5。

这是不现实的。

但是：

### 核心业务代码 ≥ 4

例如你的：

```
Agent Loop
RAG Pipeline
Chunking
Retrieval
Prompt construction
State management
Workflow
```

应该达到 4。

基础设施：

```
日志
配置加载
数据库连接
HTTP client wrapper
```

2～3 完全可以接受。

这叫：

**差异化理解。**

你没必要把精力平均分配给所有代码。

---

## 十八、还有一个非常重要的原则：核心路径尽量自己写

你以后可以把代码划成两类。

### 第一类：能力代码

这是你真正想学会的东西。

比如你现在做 Agent：

```
AgentLoop
Tool calling
Memory
Context management
Retry
State
```

这种代码不要全部让 AI 写。

AI 可以：

> 提方案。

> review。

> 提醒 bug。

> 给参考。

但其中核心 30～50% 最好自己敲。

### 第二类：劳动代码

例如：

```
Pydantic schema
CRUD
CLI 参数
serialization
API boilerplate
测试 mock
docker 配置
```

大量交给 AI 没什么问题。

你以后问自己：

> **这段代码是我需要学习的知识，还是我需要完成的劳动？**

如果是知识：

自己多做。

如果是劳动：

AI 多做。

这可以解决你现在一个非常大的困境：

> “难道以后所有代码都得自己手写？”

完全没有必要。

## 十九、给你设计一个 30 天恢复计划

你的目标不是“30 天成为大神”。

而是重新建立：

> **思考 → 实现 → 理解 → 修改**

这条神经回路。

|时间|重点|规则|
|---|---|---|
|第 1 周|停止无脑生成|AI 第一次回答禁止写代码|
|第 2 周|夺回设计权|每个功能你先写 Development Brief|
|第 3 周|夺回实现权|核心路径至少一部分自己实现|
|第 4 周|夺回维护权|回头修改 1～2 周前的代码|

### 第 1 周

只做一个改变：

> **任何新功能，AI 第一次响应不能生成实现代码。**

你必须先理解方案。

这一周不要贪多。

### 第 2 周

所有新功能：

先写：

```
输入
输出
数据流
边界
方案
疑问
```

哪怕只有 10 行。

### 第 3 周

每天找一个关键函数。

AI 不写。

自己写。

卡 30 分钟以后允许 AI：

> 给 Hint。

而不是：

> 给答案。

### 第 4 周

这是最重要的一周。

打开两周前 AI 写过的代码。

不看旧聊天。

问自己：

> 它在干嘛？

> 我能不能增加一个需求？

然后修改。

你会第一次真正看到：

> 哪些代码其实已经属于自己。

> 哪些代码从来没有进入过自己的脑子。

# 二十、每周只跟踪 4 个指标

不要跟踪：

> 今天写了几千行。

以后记录：

|指标|目标|
|---|---|
|能闭卷讲清楚的核心模块|↑|
|自己完成的核心修改|↑|
|一周后仍然能解释的模块|↑|
|遇到 Bug 后独立定位时间|↑|

特别推荐一个指标：

# 7-Day Recall

一个功能完成七天以后。

不要看文档。

回答：

```
这个模块解决什么问题？

数据怎么走？

最关键的三个函数是什么？

为什么这么设计？

如果需求变化，应该改哪里？
```

如果答不出来：

说明当时只是：

> **完成。**

没有：

> **掌握。**

---

# 二十一、你现在不需要把过去所有 AI 代码重新学习一遍

这是另一个很容易出现的错误。

你意识到问题以后可能会想：

> 我要把过去一年所有项目全部重新读一遍。

不要这么做。

这会立刻形成巨大压力。

你只需要按照：

> **未来增量原则。**

从明天开始的新代码执行新规则。

然后旧项目：

只在它重新被修改的时候补理解。

也就是：

```
新代码 → 必须理解

旧代码 → touched 时补理解
```

半年以后，大量关键代码自然会被重新覆盖。

---

# 二十二、如果你只能记住一个开发循环，就记这个

我给你压缩成：

# THINK → DESIGN → BUILD → BREAK → EXPLAIN → MODIFY

**THINK**

我到底解决什么？

↓

**DESIGN**

我打算怎么解决？

↓

**BUILD**

AI + 我，小步实现。

↓

**BREAK**

主动找边界、异常、错误。

↓

**EXPLAIN**

关闭 AI，我自己讲。

↓

**MODIFY**

我自己完成一次修改。

只有完成 MODIFY：

这个模块才算真正进入你的能力范围。

---

# 二十三、你与 AI 的关系，也应该发生一个变化

以前可能是：

> 我不知道怎么做，你帮我做。

逐渐变成：

> 我认为应该这么做，你挑战一下我的方案。

再变成：

> 这是我的实现，帮我 Review。

再变成：

> 我遇到了这个问题，这是我的三个假设，帮我检查推理。

这四句话背后代表四种完全不同的能力状态：

```
AI 代替思考
      ↓
AI 提供方案
      ↓
AI 校验思考
      ↓
AI 放大能力
```

你的目标不是离开 AI。

而是走到最后一级。

---

# 二十四、我尤其希望你停止一种行为

以后看到：

```
测试全部通过
✅ 38 passed
```

不要立刻产生：

> 爽，结束了。

给自己增加一个强制动作：

> **关掉 AI，花 15 分钟解释刚刚发生了什么。**

甚至只需要写：

```
## 今天实现了什么

## 数据怎么走

## 我为什么选择这个设计

## 我今天第一次理解了什么

## 我仍然不理解什么

## 如果明天让我修改，我应该从哪里开始
```

15 分钟。

长期来看，这 15 分钟产生的能力积累，很可能比前面 AI 帮你节省的一个小时更加重要。

---

你现在最需要的也不是突然变得特别自律，而是给自己的开发流程加几个**无法跳过的认知检查点**。

所以从下一次写代码开始，你甚至不用执行我上面全部内容。先严格执行三个规则：

1. **第一次问 AI，只讨论方案，不允许写代码。**
2. **核心代码一次只生成一个小模块，看懂以后才能继续。**
3. **功能完成后关闭 AI，自己画数据流 + 完成一次独立修改。**

连续做一个月，你对代码的感觉会明显不同。

你会慢慢从：

> “这是 AI 帮我写的项目。”

变成：

> **“这是我的项目，只是 AI 参与了实现。”**

这个区别，就是你接下来真正应该追求的能力边界。
