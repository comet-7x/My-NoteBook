## Control Flow, Guard Clauses & Boolean Clarity (MANDATORY)

1. **Guard Clauses First (Early Return / Raise)**:
   - Handle all preconditions, edge cases, and invalid states at the very top of the function.
   - Never wrap the main business logic inside an `else` block after a check; use the `if -> return/raise` pattern so the happy path stays unindented at the root level.
2. **Split Unrelated Boolean Checks (No Compound `and`/`or` Chains)**:
   - NEVER merge unrelated validation checks, permission checks, or state assertions into a single long `and`/`or` condition.
   - Split distinct checks into separate guard clauses so each failure branch can raise a specific exception with an actionable error message, or assign related sub-conditions to a self-explanatory boolean variable before branching.
3. **Avoid Clever One-Liners**:
   - Do not chain ternary operators (`a if x else b if y else c`) or nest comprehensions more than one level deep. Favor explicit multi-line loops or helper functions.
4. **Strict Typing & Tooling Gate**:
   - Every function signature must have explicit type annotations (use modern `X | None`, `list[str]`, `collections.abc.Sequence`; never `Any`).
   - All generated code must pass `ruff check --fix`, `ruff format`, and `mypy --strict` without blanket `# type: ignore` or `# noqa`.

### ❌ BAD (Compound boolean chain, deep nesting, vague error, missing types)

### ✅ GOOD (Split guard clauses, specific error messages, explicit typing, flat happy path)
```Python
def execute_transfer(
    account: Account | None,
    target: Account,
    amount: Decimal,
    user: User,
) -> Transaction:
    if account is None:
        raise AccountNotFoundError("Source account must not be None.")

    if not account.is_active or account.is_frozen:
        raise AccountStateError(
            f"Account {account.id} cannot transact (active={account.is_active}, frozen={account.is_frozen})."
        )

    if not user.has_permission("transfer"):
        raise PermissionDeniedError(f"User {user.id} lacks 'transfer' permission.")

    if target.id == account.id:
        raise InvalidTransferError(f"Cannot transfer funds to the same account ({account.id}).")

    if amount <= Decimal("0"):
        raise InvalidAmountError(f"Transfer amount must be positive, got {amount}.")

    if account.balance < amount:
        raise InsufficientFundsError(
            f"Account {account.id} balance ({account.balance}) is less than requested {amount}."
        )

    # Happy path stays completely flat at the bottom
    transaction = account.debit(amount)
    target.credit(amount)
    return transaction
```

## 一、关于 MoMA（移动模型服务平台，Mobile Model Access）带来的合作模式启发

本次大会直播宣讲中，中国移动推出 MoMA 移动模型服务平台，有两个信息值得重点关注：一是平台属于多模型聚合服务，汇聚国内多家厂商大模型，同时上线机密模型服务（当前机密模型服务以视频生成类模型为主），依托硬件隔离、机密容器实现数据可用不可见，适配政企敏感场景；二是平台提出统一量纲计费思路，尝试把语音、流量、Token 纳入同一套计量体系，打通通信资源与 AI 算力资源的账单口径，降低企业多类资源的核算成本。

基于这个底座，我有一个判断：**私企和央企、国企合作时，是否接入中国移动的算网与 MoMA 平台，会直接改变我们的交付边界**。 如果项目和中国移动开展合作，算力、模型调度、安全托管、资源计费底座由移动侧提供，我们作为合作方，重心可以聚焦在上层业务产品与服务交付，例如面向智能客服优化应答链路、搭建面向企业内部的 AI 辅助工作台（HR 自动生成 JD、运营文案创作、内部材料辅助撰写等场景），价值集中在场景理解、业务流程改造、提示词工程、知识库 RAG、应用运维等应用层能力，不需要投入底层算力基建。 如果项目不与中国移动合作，我们除了交付上层业务产品服务之外，还需要额外承担算力底座相关的工作，包括硬件选型、服务器部署、模型推理环境搭建、算力集群运维、安全合规管控等，交付链路更长、项目成本和风险点也更多。

> 补充思考（可以酌情加一句）：这种模式也意味着，未来政企客户会逐步把 “算力 + 模型” 当成和专线、带宽一样的基础通信资源，采购重心从 “买卡、搭集群” 转向 “按需调用服务”，对我们来说，方案设计要提前区分两种交付路线：**SaaS 化调用 MoMA 模式**、**本地私有化部署模式**。

## 二、信创算力选型：摩尔线程 MTT S5000 带来的新选择

本次大会 AI 芯片展区汇集华为昇腾、昆仑芯、摩尔线程等多家国产算力厂商，我重点关注了摩尔线程 MTT S5000 服务器智算卡。 过往我们做私有化部署，可选路线比较固定：无信创约束时优先英伟达 GPU；有信创合规硬性要求时，主流方案基本是华为昇腾。而本次了解到，摩尔线程 S5000（平湖架构、MUSA 全栈软件栈）已经完成 Qwen3.8-27B 模型的适配，支持 BF16/INT8 精度推理，并且通过安全可靠测评、原生支持国密算法，满足信创资质要求，同时 MUSA 生态对 CUDA 有较高兼容性，配套迁移工具，代码改造成本相对可控摩尔线程文...。

由此可以得出结论：**在有信创要求的私有化项目里，我们的算力底座确实多了一个可评估的备选方案，但不等于可以直接替换昇腾，需要做前置评估**。 需要评估的维度包括：

1. 业务侧：并发规模、时延指标、是否同时需要训练 + 推理；
2. 生态侧：客户现有信创服务器、操作系统、中间件是否和 MUSA 栈兼容；
3. 工程侧：长期运维、厂商技术支持、集群组网、多卡扩展的成熟度；
4. 成本侧：硬件采购、配套软件、迁移改造的综合 TCO。

它的价值，是打破信创算力只有昇腾一条主流路线的局面，给我们提供差异化选型空间：部分中等并发、以推理为主的私有化场景，可把摩尔线程 S5000 纳入 POC 对比清单，丰富方案报价与技术备选。
